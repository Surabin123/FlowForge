# Render deployment

This repository prepares a single-service Render deployment. No Render account connection or live deployment has been performed.

## Service design

`Dockerfile` builds the frontend with Node 22, then copies the Vite bundle into a Python 3.12 FastAPI image. FastAPI serves the UI and `/api` from one origin, so production does not need a separate static site or cross-origin API. Local development still uses Vite on port 5173 and its proxy to FastAPI on port 8000.

`render.yaml` configures the web service to follow `main`, deploy commits automatically, and use `/api/health`. It provisions a 1 GB disk at `/var/data`, with the SQLite file at `/var/data/flowforge.db` and uploaded originals under `/var/data/documents`. Database initialization uses idempotent `CREATE TABLE IF NOT EXISTS` and additive column migrations; it does not delete the database during deploy. Keep the existing database path when changing the service configuration.

The blueprint uses the paid `starter` web plan and a persistent disk. Render free web services do not provide persistent disks, and the service filesystem is ephemeral. Confirm the current price in your Render account before creating the service. Render disks attach to one service instance; do not increase the instance count. The scheduler is in the API process and has no cross-process lease. This deployment therefore does not provide high availability or multi-instance scheduling.

## Environment variables

The blueprint sets:

| Variable | Render value | Purpose |
| --- | --- | --- |
| `FLOWFORGE_REQUIRE_AUTH` | `true` | Requires a bearer token on every API route except health and auth handshake |
| `FLOWFORGE_ACCESS_TOKEN` | Generated by Render | Secret entered in the browser's FlowForge access screen |
| `FLOWFORGE_DATABASE` | `/var/data/flowforge.db` | Persistent SQLite database location |
| `FLOWFORGE_DOCUMENTS` | `/var/data/documents` | Persistent uploaded document location |
| `FLOWFORGE_ALLOWED_HOSTS` | `*` | Accepts Render's assigned service hostname |
| `FLOWFORGE_TIMEZONE` | `Asia/Calcutta` | Recurrence timezone |

The access token is stored in browser `sessionStorage` for the current tab session and sent over HTTPS as a bearer token. Use a long, unique token, do not put it in a URL, and retrieve the generated value from Render's service environment settings. Health returns only application/database status and is exempt for Render's health probe. AI and GitHub credentials are optional and should be added through Render's secret environment settings only if those integrations are needed.

## Connect and enable automatic deploys

These steps require access to the user's GitHub and Render accounts:

1. Review the local changes and run the CI commands listed in the README.
2. Commit and push the reviewed changes to the existing GitHub repository's `main` branch. This project does not need a new repository.
3. In Render, create a Blueprint instance from the existing repository and select `render.yaml`. Confirm the paid plan and disk costs before applying it.
4. Confirm the generated `FLOWFORGE_ACCESS_TOKEN` and the `/var/data` disk are present in the service configuration. Render generates the token; do not copy it into the repository.
5. Wait for the first deploy to become healthy. Open the assigned HTTPS URL, enter the token, and confirm the workspace loads.
6. Add optional provider credentials using Render's environment settings, then use the app's integration status page to confirm their configuration. Live provider calls still require their respective credentials.

After the blueprint is connected, commits pushed to `main` trigger deployments. Pull requests targeting `main` run CI but do not deploy. Render account authorization, repository connection, billing approval, initial blueprint application, and secret retrieval are manual account steps.

## Local checks and post-deploy smoke checks

Run:

```powershell
python -m pytest backend/tests -q
python -m compileall -q backend/app
npm --prefix frontend ci
npm --prefix frontend test
npm --prefix frontend run build
```

For a remote smoke check, request `https://<service-host>/api/health` and expect HTTP 200 with `status` and `database` equal to `ok`. Then open the HTTPS site, sign in with the generated token, create a disposable task, refresh the page, and verify it remains. Remove the disposable task afterward. If testing uploads, upload a disposable file, restart the service, and check that its record and original remain available.

No remote build, health check, login, persistence check, restart recovery, or provider integration has been run from this workspace.

## SQLite backup, restart, and rollback limits

Render restarts the service process during deploy. The persistent disk remains mounted, and startup initializes/migrates the same SQLite file. Workflow runs interrupted by restart are marked failed with an audit record; they do not resume mid-node. The scheduler restarts with the API process and picks up due persisted work. There is one scheduler process by design.

Create an online SQLite backup with the Python backup API, which safely includes committed pages while the database is open. On a Render shell, set `PYTHONPATH=/app/backend` and run:

```sh
python -m app.backup_database /var/data/backups/flowforge-YYYYMMDD-HHMMSS.sqlite3
```

This writes the backup onto the same disk. Copy backups off the service disk to separate storage on a regular schedule; this project does not automate or verify off-site backups or restore drills. Protect exported files because they contain personal data. Before a schema-changing release, create and retrieve a backup and confirm the previous app version remains compatible with the migrated schema.

If a deploy fails, inspect the Render build and runtime logs for the failing Docker build step, missing environment values, or database path/permission errors. Do not paste secret values into issue reports. Use Render's dashboard to redeploy the last known-good commit. This rolls back app code only; it does not reverse a SQLite migration or restore deleted user data. Restore a verified backup only after stopping the service and making a separate copy of the current database for recovery.

## Limits

The prepared configuration is not deployment verification. It does not add multi-instance locks, automated off-site backups, backup restore automation, metrics export, tracing, or high availability. A persistent disk protects against ordinary service restarts and deployments, but is not a complete backup strategy.
